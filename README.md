# Ozon price panel: конвейер данных о ценах Ozon

Небольшой data pipeline, который ежедневно наблюдает за ценами одного и того
же набора товаров Ozon и копит их историю в PostgreSQL:

```text
Discovery  ->  SKU Panel  ->  Daily Parsing  ->  PostgreSQL  ->  Historical Data
```

- **Discovery** находит товары в 3–4 категориях из `config.yaml` и отбирает
  выборку «top + случайный хвост» выдачи.
- **SKU Panel** — постоянный набор SKU (`sku_panel`), который не
  перетасовывается от запуска к запуску.
- **Daily Parsing** — существующий парсер карточек (Playwright + внутренний
  JSON API Ozon), который получает обычный список SKU.
- **PostgreSQL** — запуски, карточки, история цен и ошибки по каждому SKU.
- **Historical Data** — представления для анализа: цена вчера и сегодня,
  изменение, волатильность, динамика по категориям.

Старый сценарий «список SKU → CSV / таблица для DataLens» (`parse_ozon.py`,
Airflow DAG) работает как раньше, конвейер добавлен поверх него.

## Архитектура

```text
 config.yaml: категории, panel_size, top_ratio, расписание
        |
        v
 DISCOVERY                       python -m ozon_parser discover
   листинг категории ozon.ru (Playwright + внутренний API фронтенда)
   или отчёт data.ozon.ru «Аналитика товаров» (опционально)
   SKU из URL карточки -> дедупликация -> top + tail_random
        |
        v
 SKU PANEL                       таблица sku_panel (+ data/panel_skus.csv)
        |
        v
 DAILY PARSING                   python -m ozon_parser parse
   ежедневно: scripts/run_daily.ps1 (Планировщик заданий Windows)
   каждый SKU: открыть карточку -> JSON API -> запасной путь JSON в HTML
        |  запись сразу после разбора SKU
        v
 POSTGRESQL
   parse_runs · products · price_history · parse_errors · discovery_runs
        |
        v
 HISTORICAL DATA
   v_price_daily · v_price_latest · v_price_volatility · v_category_daily
```

Этапы связаны только данными: discovery пишет `sku_panel`, парсер её читает.
Парсер можно запустить и по обычному файлу со списком SKU, а discovery ничего
не знает о разборе карточек.

## Быстрый старт

Рабочая схема сейчас такая: **PostgreSQL — в Docker, парсинг карточек — на
хосте в Google Chrome.** В контейнере Ozon блокирует браузер на карточках
товаров, подробности — в разделе «Браузер в контейнере».

1. Установите окружение на хосте (раздел «Установка» ниже) и получите сессию
   Ozon и доступ к Gmail: `python get_cookies.py` (появятся `cookies.json` и
   `token.json`).
2. Скопируйте `.env.example` в `.env` и задайте `POSTGRES_PASSWORD`,
   `OZON_EMAIL`, `BROWSER_CHANNEL=chrome` и `PG_DSN` на базу из
   docker-compose. Пароль в `PG_DSN` — тот же, что в `POSTGRES_PASSWORD`;
   спецсимволы в нём кодируются (`@` → `%40` и т. п.):
   `PG_DSN=postgresql://ozon:<пароль>@localhost:5433/ozon`.
3. Поднимите базу (только PostgreSQL, на `localhost:5433`):

```bash
docker compose up -d
```

4. Сформируйте panel и замерьте скорость. Discovery работает и в контейнере
   (`docker compose run --rm parser python -m ozon_parser discover`):

```bash
python -m ozon_parser discover
```

```bash
python -m ozon_parser benchmark
```

5. Зарегистрируйте ежедневный прогон в Планировщике заданий Windows (время —
   из `config.yaml`, см. «Ежедневный запуск»):

```bash
powershell -ExecutionPolicy Bypass -File scripts\register_windows_task.ps1
```

6. Первый прогон можно запустить вручную, не дожидаясь расписания:

```bash
python -m ozon_parser parse
```

Миграции схемы применяются автоматически при старте любой команды, запускать
SQL руками не нужно.

Если используете контейнер для разовых команд: `config.yaml` подключён в него
как файл, правки действуют со следующей команды. Код копируется в образ при
сборке, поэтому после обновления кода образ нужно пересобрать (данные в базе
сохраняются):

```bash
docker compose build parser
```

## Discovery: откуда берутся SKU

### data.ozon.ru: проверено, подходит частично

Сначала проверен официальный сервис Ozon для продавцов — `data.ozon.ru`
(«Что продавать на Ozon»), куда проект и так входит в `get_cookies.py`.
Результаты на живом сервисе 29.09.2026:

- раздел «Аналитика товаров» (`/app/bestsellers`) получает данные запросом
  `POST /p-api/exa-auth/analytics_what_to_sell/what_to_sell` с телом
  `{"filter": {"categories": [...], "brandIds": []}, "limit": "50",
  "offset": "0", "sort": {"attribute": "sum_gmv", "order": "desc"}}`;
- в ответе есть `sku`, ссылка на карточку, категория, продажи и выручка
  за 28 дней;
- `limit` не больше 100 («limit must be ... less than or equal to 100»);
- `offset` меньше 1000 («offset limit exceeded»), `totals` = 1000. Значит, по
  любому фильтру доступно только окно из 1000 строк, отсортированных по
  метрике. Сортировка `asc` отдаёт другой край (товары с 1 продажей), а
  середину распределения получить нельзя;
- нужна авторизованная сессия `data.ozon.ru`. Во время разведки сессия,
  сохранённая в `cookies.json`, через несколько запусков браузера
  перестала приниматься (редирект на вход Ozon ID): токены обновляются на
  лету, и без сохранения нового состояния файл устаревает. Поэтому discovery
  сохраняет обновлённую сессию после удачной работы с `data.ozon.ru`;
- фильтр по категории — список id узлов дерева `get_seller_tree_v2`: для
  уровней 1–2 это `descriptionCategoryId`, для 3-го — `descriptionTypeId`
  (например, «Смартфон» — `95139`). Формат взят из кода фронтенда
  `data.ozon.ru`. **Вживую запрос с фильтром не проверен:** к этому моменту
  сессия уже была недействительна.

Вывод: источник реальный и дешёвый (10 запросов на 1000 SKU), но это выборка
из топ-1000 категории по продажам, и «хвост» в нём — хвост лидеров, а не
категории. Он реализован как опциональный источник `source: data_ozon`
(пример закомментирован в `config.yaml`). По умолчанию используется листинг
ozon.ru.

### Листинг категории ozon.ru (по умолчанию)

Страница категории открывается в Playwright: так проходит антибот-проверка и
подхватываются cookies. Страницы выдачи запрашиваются у того же внутреннего
API, которым пользуется фронтенд:

```text
/api/entrypoint-api.bx/page/json/v2?url=/category/smartfony-15502/?page=N
```

Что выяснено на живом сайте (29.09.2026):

- товары лежат в виджете `tileGridDesktop`, **по 8 на страницу**. Страницы
  идут подряд без пересечений; HTML-страница `?page=N` показывает блоки N и
  N+1. При повторном запросе той же страницы 7–8 товаров из 8 совпадают;
- выдача обрывается на **646–684-й странице** (~5200–5400 позиций) во всех
  четырёх категориях, включая нишевую: похоже, Ozon ограничивает глубину
  числом позиций, а не размером категории. Поэтому `tail_max_page: 600`;
- ссылка на карточку — `/product/<slug>-<sku>/?at=...`. SKU берётся из URL
  (`sampling.sku_from_url`), а не из вёрстки;
- slug в адресе категории роли не играет: Ozon определяет категорию по
  числовому id (`/category/kofemashiny-10680/` открывает «Утюги»). Адреса в
  `config.yaml` проверены через поиск Ozon.

Алгоритм для категории:

```text
открыть страницу категории
  -> top:  страницы 1, 2, ... подряд, пока не наберётся top_size новых SKU
  -> tail: случайные страницы из [после зоны top .. tail_max_page],
           с каждой не больше tail_items_per_page товаров
           (пустая страница = выдача кончилась, диапазон сужается)
  -> SKU из URL -> дедупликация (в том числе с другими категориями panel)
  -> запись в sku_panel: position, page, sampling_group
```

Запрашиваются только нужные страницы, строго последовательно. Параметры темпа
в `config.yaml` подобраны по живому опыту:

- **Пауза.** `request_delay` = 5 с от конца предыдущего запроса, со случайным
  разбросом ±30 % (`request_jitter`). Между категориями — `category_pause`
  = 60 с.
- **Почему не быстрее.** Первая версия шла с паузой 2 с от начала запроса и
  при сборе полной panel в Docker (29.09.2026) после ~110 запросов получила
  **HTTP 403 на все запросы к выдаче**. Одна категория собралась, три — нет.
- **Отдельная сессия браузера на категорию.** Во втором прогоне в Docker
  (уже с паузой 5 с) картина повторилась: `smartphones` в свежем браузере
  собралась целиком (79 страниц без единого предупреждения), а
  `coffee_machines` в той же сессии получила 403 на первом же запросе и не
  получила ответа за 10 минут ожидания. Оба раза блок начинался на смене
  категории внутри одной сессии, а не после определённого числа запросов
  (110 и 81) или минут (4 и 8). Поэтому каждая категория обходится в новом
  контексте браузера (чистые cookies и состояние, cookies из `cookies.json`
  загружаются заново). **Это вывод из двух прогонов, а не документированное
  поведение Ozon.**
- **Отказ Ozon** (403 / 429 / антибот-заглушка вместо JSON). Короткие повторы
  его только продлевают, поэтому discovery ждёт по списку `block_backoff`
  (10 с, 1, 3, 5 мин) и каждый раз повторяет в **новой** сессии браузера.
- **Если ограничение не снялось,** discovery сохраняет в panel всё, что уже
  нашёл, в том числе частично собранную категорию, и не трогает следующие
  категории. Повторный `discover` через 30–60 минут пропустит готовое и
  доберёт недостающее.
- **Обычные сбои** (обрыв, пустой ответ) — 2 коротких повтора (`MAX_RETRIES`),
  после чего страница пропускается.

Пилотная panel из 80 SKU потребовала 29 запросов к листингу.

### Sampling

**Почему несколько категорий.** Цены в разных нишах ведут себя по-разному:
дешёвые массовые товары с сотнями продавцов (чехлы), дорогая электроника с
частыми акциями (смартфоны), товары длительного пользования (кофемашины),
узкая ниша с малым спросом (аксессуары для струнных инструментов). Одна
категория показала бы динамику одного типа рынка.

**Почему top + tail, а не первые N.** Верх выдачи — самые популярные и
продвигаемые карточки, в том числе рекламные. Panel только из них показала
бы, как меняются цены лидеров, а не категории. Поэтому доля `top_ratio`
(по умолчанию 0.4) panel — первые позиции выдачи (`sampling_group = top`), а
остальное — случайные товары со случайных глубоких страниц
(`tail_random`). С одной страницы хвоста берётся не больше 3 товаров
(`tail_items_per_page`), чтобы выборка растянулась по глубине, а не собралась
с пары страниц. Категория `phone_cases` 29.09.2026 собрана ещё с 2 товарами
со страницы. Доли, глубина
и зерно генератора задаются в `config.yaml`.

**Почему panel фиксированная.** Динамика цен имеет смысл только на одних и
тех же товарах: если каждый день брать новую случайную выборку, изменение
«средней цены» будет отражать смену состава, а не движение цен. Поэтому:

- повторный `discover` не трогает уже активные SKU: upsert обновляет только
  выключенные строки. Если категория набрана до `panel_size`, discover её
  пропускает без браузера и без запросов к Ozon;
- если `panel_size` увеличить, discover **доберёт** недостающие SKU в каждой
  группе, не меняя существующих;
- полная пересборка возможна только явно: `discover --rebuild`. Старые строки
  не удаляются, а выключаются (`is_active = false`), история по ним остаётся;
- SKU уникален во всей panel: товар, найденный в двух категориях, попадает
  только в первую.

Генератор случайных чисел инициализируется парой `(discovery.seed, категория)`:
при той же выдаче Ozon случайная часть воспроизводится.

### Dataset bias

Выборка формируется из ранжированной выдачи Ozon и поэтому не является
статистически случайной выборкой всех товаров площадки. Panel предназначена
для наблюдения динамики выбранного набора товаров во времени, а не для оценки
всей генеральной совокупности Ozon.

Конкретнее:

- кандидаты — только то, что Ozon показывает в выдаче категории при
  сортировке «Популярные». Товары без остатка, скрытые и не попавшие в выдачу
  в неё не входят;
- глубина ограничена самим Ozon (выдача обрывается на нескольких тысячах
  позиций) и настройкой `tail_max_page`. Длинный хвост категорий с сотнями
  тысяч товаров недоступен;
- «случайный хвост» случаен относительно ранжирования Ozon, а оно зависит от
  продаж, рекламы и персонализации (выдача немного меняется от запроса к
  запросу);
- категории выбраны вручную, их 4, и они не представляют Ozon в целом;
- со временем panel «стареет»: товары снимаются с продажи и становятся
  недоступными. Это видно по `is_available` и ошибкам `not_found`. Подмена
  выбывших SKU намеренно не автоматическая.

## PostgreSQL

Схема задаётся файлами `ozon_parser/migrations/NNNN_*.sql`. Они применяются по
порядку номеров, каждый ровно один раз (учёт — в `schema_migrations`), под
advisory lock и одной транзакцией. Любая команда `python -m ozon_parser`
сначала проверяет миграции, поэтому свежая база готова после первого запуска.

| Таблица          | Что хранит                                                              |
| ---------------- | ----------------------------------------------------------------------- |
| `sku_panel`      | Panel: `sku` (уникален), `category`, `source`, `source_url`, `position`, `page`, `sampling_group` (`top` / `tail_random`), `is_active`, `first_seen_at` / `last_seen_at` (когда discovery видел товар в выдаче), `created_at`, `updated_at`, `deactivated_at` |
| `discovery_runs` | Запуски discovery: категория, источник, seed, запросов, найдено, отобрано |
| `parse_runs`     | Запуски парсера: `kind` (`daily` / `manual` / `benchmark`), `status`, `started_at`, `finished_at`, `total_sku`, `processed_count`, `success_count`, `error_count`, `duration_seconds`, `sku_per_minute`, `avg_sku_seconds`, `request_delay` |
| `products`       | Последние атрибуты карточки: название, картинка, цвет, материал, комплектация, фото/видео, rich-контент |
| `price_history`  | Наблюдение на момент сбора: `collected_at`, `price`, `card_price` (с Ozon Картой), `old_price` (зачёркнутая), `discount_pct`, `is_available`, `rating`, `reviews_total`, `source`, `run_id` |
| `parse_errors`   | Ошибка по SKU: `run_id`, `sku`, `occurred_at`, `error_type`, `error_message`, `attempts` |

Решения по схеме:

- «медленные» атрибуты карточки (название, характеристики) лежат в
  `products` один раз и обновляются. Меняющиеся каждый день (цена, наличие,
  рейтинг, отзывы) — в `price_history`, строка на каждый успешный сбор.
  Данные не дублируются;
- `collected_at` — момент разбора карточки, а не дата запуска и не имя файла;
- история не перезаписывается: ключ `(run_id, sku)`. Новый прогон — новые
  строки. Повтор записи внутри того же прогона обновляет ту же строку;
- карточка, собранная запасным путём (JSON в HTML), не затирает известные
  характеристики пустыми (`COALESCE`);
- два прогона парсера одновременно невозможны (`pg_try_advisory_lock`), а
  прогон, брошенный упавшим процессом, помечается `interrupted` при старте
  следующего;
- таблица `ozon_products` старого сценария не затрагивается.

Какая цена была вчера и какая сегодня, насколько изменилась:

WHERE observed_date = current_date AND price_change <> 0
ORDER BY abs(price_change_pct) DESC;

## Performance

Все цифры — из `parse_runs` фактических прогонов 29.09.2026, ничего не
пересчитано вручную. Условия: Windows 11, домашний интернет, Google Chrome
(`BROWSER_CHANNEL=chrome`) в фоновом режиме (`HEADLESS=1`), один браузер,
SKU строго последовательно, `REQUEST_DELAY=3.0`, `MAX_RETRIES=2`.

| run | Тип                      | SKU | Время    | SKU/мин | Разбор SKU, среднее | Успех | Ошибки |
| --- | ------------------------ | --- | -------- | ------- | ------------------- | ----- | ------ |
| 2   | `benchmark` (50 случайных SKU panel) | 50 | 5m 46s  | 8.66 | 3.9 с | 100% | 0 |
| 3   | `parse` (вся пилотная panel)         | 80 | 9m 08s  | 8.76 | 3.8 с | 100% | 0 |
| 4   | `schedule --once` → `parse --kind daily` | 90 | 10m 18s | 8.74 | 3.8 с | 100% | 0 |
| 5   | `scripts/run_daily.ps1` (01.10.2026)     | 118 | 12m 48s | 9.21 | 3.5 с | 100% | 0 |

- **SKU/мин** — обработанные SKU, делённые на полное время прогона, включая
  запуск браузера и паузы.
- **Разбор SKU** — от открытия карточки до готовой записи, с повторами. К нему
  добавляется пауза `REQUEST_DELAY` = 3 с, итого около 6,9 с на товар (в
  старом README было 10–15 с).
- Запасной путь (JSON в HTML) понадобился в 2 наблюдениях из 223: у одной
  карточки API стабильно отвечал 403.

Вывод `benchmark`:

```text
Benchmark (run_id=2, status=success)
  Total SKU:        50
  Duration:         5m 46s
  Speed:            8.66 SKU/min
  Avg parse time:   3.9 s/SKU (+ пауза 3.0 с между SKU)
  Success:          50 (100.0%)
  Errors:           0 (0.0%) -
  Daily capacity:   8 h x 8.66 SKU/min = 4157 SKU
  Recommended panel (x0.8 запас): ~3325 SKU
```

**Дневная ёмкость:** 8 ч × 8,7 SKU/мин ≈ 4 170 SKU; с запасом ×0,8 — около
3 330 SKU.

**Выбранный размер panel — 4 × 300 = 1 200 SKU** (120 top + 180 tail в каждой
категории): около 2,3 ч в сутки при измеренной скорости. Это примерно треть
расчётной ёмкости, и вот почему:

- самый длинный замеренный прогон — 10 минут. Как антибот Ozon поведёт себя
  на многочасовом ежедневном прогоне, не измерено;
- нужен запас на повторы, перезапуски браузера и медленные дни;
- меньше нагрузка на Ozon.

Как масштабировать: после первых ежедневных прогонов посмотреть
`python -m ozon_parser runs` (скорость полного прогона `daily`), увеличить
`panel_size` в `config.yaml` и запустить `discover` — он доберёт недостающие
SKU, не трогая существующие.

**Discovery.**

- **Пилотная panel** (4 × 20): 29 запросов к листингу, около минуты. Донабор
  +10 SKU — 4 запроса.
- **Полная категория в Docker** (29.09.2026, пауза 2 с): `phone_cases` —
  300 SKU за 110 запросов (15 страниц top + 90 хвоста по 2 товара + повторы),
  около 4 минут. Сразу после этого Ozon стал отвечать 403, отсюда нынешний
  темп.
- **С нынешними настройками** (5 с ± 30 %, 3 товара со страницы хвоста) на
  категорию нужно около 75 запросов, примерно 8–9 минут. На три оставшиеся
  категории с паузами — около получаса. **Это оценка, а не замер.**

## Ежедневный запуск

Каждый день в `schedule.daily_at` (сейчас 18:00 по Москве) выполняются два шага
отдельными процессами — это команда `python -m ozon_parser schedule --once`:

```text
ensure_session (get_cookies.py --non-interactive --max-age-days 14)
    -> parse --kind daily
         -> активные SKU из sku_panel
         -> парсинг, запись каждого SKU в products / price_history
         -> parse_runs (итог и скорость), parse_errors (причины)
```

Отдельные процессы нужны для изоляции: браузер и драйвер Playwright умирают
вместе с прогоном и не копят память от ночи к ночи. Прогоны идут строго по
очереди, у прогона есть жёсткий предел длительности
(`schedule.parse_timeout_hours`). Если обновить сессию не удалось, парсинг
всё равно запускается: карточки ozon.ru открываются и без входа.

**Сейчас — Планировщик заданий Windows на хосте.** Скрипт
`scripts/register_windows_task.ps1` регистрирует задачу `OzonParserDaily`,
которая запускает `scripts/run_daily.ps1` (Chrome без окна, `HEADLESS=1`).
Особенности задачи:

- **Время.** Берётся из `config.yaml` и переводится в местное время Windows:
  18:00 МСК на машине с UTC+7 — это 22:00. После смены `daily_at` скрипт
  регистрации нужно запустить ещё раз.
- **Учётная запись.** Задача выполняется от текущего пользователя, только
  когда он вошёл в систему. Пароль Windows не нужен и не сохраняется.
- **Пропущенное время.** Если компьютер был выключен, задача запустится при
  первой возможности.
- **Повторы.** Второй экземпляр не стартует, пока идёт первый; жёсткий предел
  прогона — 10 ч.
- **Проверить или удалить:**
  `Get-ScheduledTask -TaskName OzonParserDaily | Get-ScheduledTaskInfo`,
  `Unregister-ScheduledTask -TaskName OzonParserDaily`.

**Контейнерный планировщик** (`python -m ozon_parser schedule` — простой цикл
до времени `daily_at`) лежит в docker-compose под профилем и по умолчанию не
стартует: в контейнере Ozon блокирует браузер на карточках (см. «Браузер в
контейнере»). Включить, когда это будет исправлено:
`docker compose --profile container-scheduler up -d`.

Airflow DAG (`dags/ozon_parser_dag.py`) по-прежнему обслуживает старый
сценарий. Чтобы перевести его на panel, достаточно заменить команду задачи
`parse_products` на `python -m ozon_parser parse --kind daily`.

### Браузер в контейнере

30.09.2026 первый ежедневный прогон шёл в контейнере и почти целиком провалился:

- Встроенный Chromium от Playwright (headless, Linux) получал **HTTP 403 от
  API каждой карточки**, на каждой странице показывалась антибот-проверка.
- В HTML за первым товаром данных тоже не было.
- За 5 ч 19 мин: 1 успешный SKU, 953 ошибки `fetch_error`; в 23:19 процесс
  оборвался вместе с остановкой компьютера.
- Повторный тест в контейнере 01.10: 1 из 3.
- Те же SKU с того же IP в Google Chrome на хосте: 3 из 3 через API.

Вероятная причина — отпечаток браузера: headless-сборка Chromium и
User-Agent «Windows» на Linux. Возможное исправление: настоящий Google
Chrome в образе, User-Agent под Linux, при необходимости Chrome с окном на
виртуальном экране (Xvfb). Это пока не сделано и не проверено. Discovery
(листинг категорий) в контейнере при этом работает.

### Предохранитель

Если Ozon не отдаёт данные `MAX_CONSECUTIVE_FAILURES` (по умолчанию 10) SKU
подряд, прогон останавливается сам:

- Ответ «товара нет» (404) серию не продолжает.
- Прогон получает статус `blocked`, необработанные SKU пишутся в
  `parse_errors` с типом `blocked`, код возврата — 1.
- Повод — тот же прогон 30.09: без предохранителя парсер 5 часов делал по 3
  попытки на каждый товар, нагружая Ozon впустую.

Порядок SKU в прогоне — `md5(sku)`: стабильный и перемешанный между
категориями. Если прогон оборвётся по таймауту, недобор распределится по
категориям равномерно.

## Шаг 1 — получить cookies

```bash
python get_cookies.py
```

Перед первым запуском привяжите к аккаунту Ozon (профиль Ozon ID) тот Gmail,
к которому выдан доступ через Gmail API, и укажите его в `.env` как `OZON_EMAIL`.

Как устроен вход (проверено на живом сайте):

1. `data.ozon.ru` сначала отдаёт антибот-проверку: HTTP 403, страница
   `Antibot Challenge Page`. Это JS-проверка браузера, через 5–10 секунд она
   сама перезагружает страницу. Скрипт её дожидается (`CHALLENGE_TIMEOUT`).
2. На лендинге формы нет: вход начинается с кнопки «Перейти к аналитике»,
   которая уводит на `sso.ozon.ru` (Ozon ID).
3. В Ozon ID скрипт выбирает «Войти по почте» и вводит `OZON_EMAIL`.
4. Ozon присылает письмо с кодом. Скрипт находит свежее письмо через Gmail API
   (в том числе в «Спаме») и вводит код.
5. После появления cookies авторизации состояние сессии (cookies +
   localStorage) сохраняется в `cookies.json`.

К Gmail скрипт подключается **до** запроса кода: если доступа к почте нет,
попытка входа на Ozon не тратится.

**Почему по почте, а не по телефону.** При входе по телефону способ
подтверждения выбирает сам Ozon: QR-код в приложении, звонок с вводом
последних цифр номера, SMS или письмо. Письмо в этом списке не
гарантировано, а остальные способы через Gmail не автоматизируются. Вход по
почте — единственный путь, где код гарантированно приходит письмом. Вход по
телефону тоже реализован (`LOGIN_METHOD=phone` или `--method phone`):
- код страны +7 в форме выбран отдельно, поэтому вводится только национальная
  часть номера;
- после ввода скрипт сверяет, что приняла маска поля;
- если Ozon предлагает доставку кода на почту, скрипт её выбирает;
- если Ozon выбрал QR-код или звонок, скрипт сразу останавливается с
  объяснением, а не ждёт письмо, которое не придёт.

При неудачном входе снимок экрана сохраняется в `logs/get_cookies_failure.png`.

Если сессия уже сохранена, повторный запуск ничего не делает. Перезаписать
её можно флагом `--force`. Если автоматический вход невозможен (например,
Ozon просит капчу), войдите вручную: скрипт откроет браузер и подождёт, пока
вы войдёте (`MANUAL_LOGIN_TIMEOUT`).

```bash
python get_cookies.py --manual
```

## Шаг 2 — распарсить товары по списку (старый сценарий)

Для ежедневного наблюдения за panel используйте `python -m ozon_parser parse`

| `videos_seller`    | Количество видео                             | `webGallery.videos`                                  |
| `color`            | Цвет                                         | характеристики, запасной — `webAspects`              |
| `material`         | Материал                                     | характеристики                                       |
| `art_set`          | Артикул производителя / комплектация         | характеристики                                       |
| `has_rich_content` | Есть ли в описании картинки, таблицы, списки | `webDescription`                                     |

Поля, которых у товара нет, остаются пустыми, и это не ошибка парсинга.
Характеристики ищутся по названию с приоритетом: полное совпадение, затем
совпадение начала, затем вхождение. Известные ловушки исключены: «Количество
цветов» не считается цветом, «Состав комплекта» — материалом, а характеристика
«Артикул» у Ozon равна самому SKU.

В таблицах БД есть ещё две служебные колонки:
- `parsed_date` — дата среза;
- `source` — `api` или `html`, то есть откуда взяты данные (см. ниже).

В CSV этих колонок нет, там ровно 12 полей задания.

Для истории цен (`price_history`) из того же виджета `webPrice` берутся ещё
четыре поля. Их структура проверена на живых карточках 29.09.2026:

| Поле           | Описание                                       | Источник                                        |
| -------------- | ---------------------------------------------- | ----------------------------------------------- |
| `card_price`   | Цена с Ozon Картой                             | `webPrice.cardPrice`                            |
| `old_price`    | Зачёркнутая цена «до скидки»                   | `webPrice.originalPrice` (если `showOriginalPrice`) |
| `discount_pct` | Скидка `price` относительно `old_price`, %     | вычисляется                                     |
| `is_available` | Товар в наличии                                | `webOutOfStock` → нет; `webPrice.isAvailable`, `webSale.offer.isAvailable`, запасной — JSON-LD `availability` |

В CSV и таблицу `ozon_products` они не попадают.

## Как устроен парсинг

**Почему браузер, а не `requests`.** Ozon закрыт антибот-защитой. Запрос из
`requests.Session` даже с действующими cookies из `cookies.json` получает
HTTP 403 и на API, и на HTML-страницу: защита проверяет, что запрос сделал
настоящий браузер (JS-проверка, отпечаток TLS). Поэтому сессия поднимается в
Playwright. Cookies из файла загружаются в контекст браузера так же, как в
`requests.Session` загружался бы cookie jar, а запросы к API выполняются из
страницы и несут эти cookies.

**Основной путь — внутренний JSON API**, из которого фронтенд собирает страницу:

```
/api/entrypoint-api.bx/page/json/v2?url=/product/<sku>/
```

Ответ — объект с `widgetStates`: состояния виджетов в виде JSON-строк. Две
особенности, выясненные на живых карточках:

1. Карточка отдаётся двумя запросами. Описание и полный список характеристик
   лежат во второй части (`layout_page_index=2`), без неё `art_set` и
   `has_rich_content` остаются пустыми. Парсер забирает обе части и склеивает.
2. Запрос проходит только из вкладки с открытой карточкой, иначе Ozon отвечает
   403. Поэтому парсер сначала открывает страницу товара.

**Запасной путь — JSON, встроенный в HTML карточки.** Сервер отдаёт первую
часть страницы уже отрисованной. Каждый виджет в ней —
`<div id="state-webPrice-…" data-state='{…}'>` с тем же JSON, что и в
`widgetStates`. Рядом лежит блок `<script type="application/ld+json">` со
schema.org Product. Оба извлекаются стандартным `html.parser` и разбираются
тем же кодом, что и ответ API. Недостающие поля добираются из JSON-LD. В
HTML нет описания и полных характеристик, поэтому у таких записей
`source = html`, а `art_set` и `has_rich_content` пусты.

Rich-описание у Ozon бывает двух видов, и оба учитываются: структурный
`richAnnotationJson` с блоками (картинки, таблицы, списки) и HTML-текст в
`richAnnotation`.

## Ежедневный запуск через Airflow (старый сценарий)

DAG лежит в [`dags/ozon_parser_dag.py`](dags/ozon_parser_dag.py) и состоит из
трёх задач:

```
ensure_session  ->  parse_products  ->  check_result
```

- **ensure_session** — `get_cookies.py --non-interactive --max-age-days N`.
  Если сессия действительна и моложе `ozon_cookies_ttl_days`, задача сразу
  завершается. Если файла нет, он повреждён, в нём нет токенов или он старше
  лимита, выполняется автоматический вход по почте с кодом из Gmail, и
  `cookies.json` перевыпускается. Человек при этом не нужен.
  `--non-interactive` запрещает шаги, которые на сервере некому пройти (ручной
  вход и окно согласия Google): если они понадобились, задача падает с
  понятной причиной, а не зависает.
- **parse_products** запускает парсер в фоновом режиме (`HEADLESS=1`).
- **check_result** вызывает `check_snapshot.py` и падает, если за эту дату в
  хранилище не появилось строк.

Все шаги запускаются отдельными процессами в окружении проекта. У воркера
Airflow обычно нет ни Playwright, ни драйверов БД, поэтому DAG не импортирует
пакет проекта и не тянет его зависимости.

Перед первым запуском на сервер нужно положить `credentials.json` и
`token.json`. `token.json` создаётся при первом запуске `get_cookies.py` на
машине с браузером: там откроется окно согласия Google, а на сервере его
открыть некому. Дальше токен обновляется сам. Исключение — OAuth-приложение в
Google Cloud в статусе **Testing**: у него refresh-токен живёт 7 дней, поэтому
для постоянной работы приложение нужно перевести в **Production**.

Переменные Airflow (Admin → Variables):

| Переменная              | По умолчанию        | Назначение                                |
| ----------------------- | ------------------- | ----------------------------------------- |
| `ozon_project_dir`      | `/opt/ozon_parser`  | каталог проекта на сервере                |
| `ozon_python`           | `.venv/bin/python`  | интерпретатор окружения проекта           |
| `ozon_storage`          | `postgres`          | `csv` / `postgres` / `clickhouse`         |
| `ozon_cookies_ttl_days` | `14`                | через сколько дней входить заново         |
| `ozon_min_rows`         | `1`                 | сколько строк минимум ждём за день        |
| `ozon_min_success_rate` | `0.8`               | доля успешных SKU, ниже которой — провал  |

Расписание — `30 5 * * *` по Москве, `catchup=False`, `max_active_runs=1`.
Дата среза передаётся парсеру через `--date {{ data_interval_end | ds }}`:
это день запуска, а не начало интервала, поэтому перезапуск задачи за прошлые
сутки запишет данные тем же числом. Повторный запуск за тот же день не
плодит дубли: PostgreSQL обновляет строку через `ON CONFLICT (sku, parsed_date)`,
ClickHouse — движком `ReplacingMergeTree`.

DAG совместим с Airflow 2.x и 3.x: операторы импортируются из провайдера
`standard`, а при его отсутствии — по старым путям. Под Windows Airflow не
работает, нужен Linux, WSL2 или Docker.

## Обработка ошибок

Обрабатываются и логируются:

- нет доступа к почте, письмо не пришло за таймаут, код не распознан в письме;
- старое письмо с предыдущим кодом — отсекается по времени запроса;
- антибот-проверка — ожидание её прохождения, отказ по таймауту;
- не найдены кнопка входа, поле почты, телефона или кода (изменилась вёрстка);
- маска поля исказила номер — код не запрашивается;
- Ozon выбрал подтверждение через QR-код или звонок — остановка с объяснением;
- таймаут загрузки, сетевые сбои — повторы (`MAX_RETRIES`);
- API карточки недоступен — данные из JSON в HTML;
- несуществующий SKU (HTTP 404) — без бессмысленных повторов;
- браузер упал или закрыт посреди списка — перезапуск (`MAX_BROWSER_RESTARTS`),
  SKU, на котором он упал, обрабатывается заново;
- временные сбои Gmail API (429, 5xx) — экспоненциальная пауза;
- прерывание по Ctrl+C — собранное сохраняется;
- недоступная БД или недоступный CSV — одно не блокирует другое.

В конвейере (`python -m ozon_parser parse`) дополнительно:

- каждый SKU пишется в PostgreSQL сразу после разбора, до следующего SKU;
  проблемный SKU не останавливает прогон, его причина попадает в
  `parse_errors` (`not_found`, `fetch_error`, `timeout`, `browser_error`,
  `storage_error`, `not_processed`, `interrupted`) вместе с числом попыток;
- SKU, до которых не дошла очередь (браузер падал чаще
  `MAX_BROWSER_RESTARTS`, прогон прерван, не открылся файл сессии), тоже
  попадают в `parse_errors`, а не пропадают молча;
- обрыв соединения с PostgreSQL — одна повторная попытка на новом соединении;
  если запись всё равно не прошла, SKU считается ошибкой `storage_error`;
- второй одновременный прогон отказывается стартовать (advisory lock), а
  прогон, брошенный упавшим процессом, помечается `interrupted`;
- серия из `MAX_CONSECUTIVE_FAILURES` SKU подряд без данных (кроме 404)
  останавливает прогон со статусом `blocked` — предохранитель от многочасовых
  запросов к Ozon, когда он блокирует (см. «Предохранитель»);
- в discovery отказ Ozon (403 / 429 / антибот-заглушка) — выжидание по
  `block_backoff` с повторным открытием категории. Если отказ не снялся,
  найденное сохраняется, оставшиеся категории не запускаются (статус
  `stopped`), и повторный `discover` доберёт остальное. Обычный сбой страницы
  — короткие повторы и пропуск страницы. Итог каждой категории пишется в
  `discovery_runs`. Если хоть одна категория не собрана до `panel_size`,
  `discover` возвращает код 1.

Пустой прогон не считается успешным: парсер возвращает 1, а CSV
перезаписывается одним заголовком, чтобы не выдать снимок прошлого запуска за
сегодняшний.

Логи пишутся в консоль и в `logs/<модуль>.log` с ротацией (10 МБ, 5 файлов).

  `scripts/run_daily.ps1` целиком (ensure_session → parse) на локальной
  тестовой базе — 118 из 118 SKU, ни одного 403, 9,21 SKU/мин;
- задача `OzonParserDaily` зарегистрирована в Планировщике заданий Windows

Не проверено вживую: исправление браузера в контейнере (не делалось),

## Ограничения

- Селекторы формы входа (`*_SELECTORS` в `ozon_parser/login.py`) и имена
  виджетов (`W_*` в `ozon_parser/extract.py`) заданы списками с запасными
  вариантами. При изменениях на сайте править нужно их.
- Ключевые слова характеристик (`COLOR_KEYS`, `MATERIAL_KEYS`, `ART_SET_KEYS`)
  подобраны на товарах одной категории. У других категорий названия могут
  отличаться, и тогда списки нужно дополнить.
- Парсинг последовательный: около 7 с на товар вместе с паузой
  `REQUEST_DELAY` = 3 с (замеры — в разделе Performance). `REQUEST_DELAY` не
  стоит занижать, а параллельность намеренно не добавлялась, чтобы не
  увеличивать нагрузку на Ozon.
- Discovery опирается на внутренний API фронтенда Ozon (`entrypoint-api`) и
  виджет `tileGridDesktop` — это не публичный API. Если Ozon изменит формат,
  discovery остановится с понятной ошибкой в `discovery_runs`, а уже
  собранная panel и ежедневный парсинг продолжат работать.
- Источник `data_ozon` реализован по данным разведки, но запрос с фильтром по
  категории вживую не проверен (см. «Discovery»).
- Выбывшие из продажи SKU остаются в panel (с `is_available = false` или
  ошибками `not_found`); автоматической замены нет, пересборка — только явно
  (`discover --rebuild`).
- **Парсинг карточек в Docker сейчас не работает:** Ozon отвечает 403
  встроенному Chromium из образа (см. «Браузер в контейнере»). Поэтому
  ежедневный прогон идёт на хосте в Google Chrome, а компьютер должен быть
  включён в назначенное время. Для VPS контейнерный браузер придётся чинить.
- Ozon ограничивает частоту запросов к листингу; точный порог неизвестен
  (при паузе 2 с — после ~110 запросов). Нынешний темп (5 с ± 30 %) выбран с
  запасом, но гарантий нет: если Ozon снова ответит 403, discovery сохранит
  собранное и остановится до следующего запуска.
- Сессия Ozon живёт ограниченное время. В DAG она перевыпускается
  автоматически раз в `ozon_cookies_ttl_days`. Если Ozon отозвал её раньше,
  перевыпустите сессию вручную: `python get_cookies.py --force`.
- Антибот Ozon может строже относиться к IP-адресам дата-центров, чем к
  домашним. Вход и парсинг в фоновом режиме проверены с обычного адреса. На
  сервере первый запуск DAG стоит провести под наблюдением.
- Автоматизированный сбор данных с ozon.ru — зона риска по пользовательскому
  соглашению сайта. Для продакшена этот вопрос стоит проговорить заранее.

## Секреты

`.env`, `credentials.json`, `token.json` и `cookies.json` содержат секреты и
перечислены в `.gitignore`:
- `token.json` — доступ на чтение всей почты;
- `cookies.json` — действующая сессия Ozon.

Не передавайте их ни в репозитории, ни в архиве с проектом. `token.json` и
`cookies.json` создаются с правами `0600`. На Windows POSIX-права не
действуют, и доступ там можно ограничить только через ACL.

В Docker-образ секреты не попадают (`.dockerignore`): docker-compose
подключает их томами при запуске, а пароль PostgreSQL берёт из `.env`
(`POSTGRES_PASSWORD`). В Python-коде и `config.yaml` учётных данных нет.
