# ADR 0002. Данные нескольких маркетплейсов — в общих таблицах с колонкой `marketplace`

- Статус: принято 09.10.2026, реализовано миграцией `0004_multi_marketplace`
  10.10.2026. Сырые ответы (`raw_responses`) и строка `wb` в справочнике
  появятся вместе с адаптером Wildberries
- Связано: issue [#4](https://github.com/Dannke/ozon-parser/issues/4) — регион
  как измерение наблюдения

## Контекст

Сейчас в таблицах `sku_panel`, `products`, `price_history`, `parse_runs`,
`parse_errors` и `discovery_runs` лежит только Ozon, ключ товара — `sku`.
Артикулы Wildberries (`nm id`) — тоже числа, и с артикулами Ozon они могут
совпасть.

Соседний проект ozon-market-analytics (dbt) читает эти таблицы напрямую,
со своими явными списками колонок, и группирует данные по одному `sku`.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| ------- | ----- | ------ |
| Таблицы на маркетплейс (`wb_price_history`, …) | Ничего не меняется для Ozon | Дублирование DDL, SQL и представлений на каждый маркетплейс; сравнение маркетплейсов — только через `UNION`. Классический антипаттерн |
| Схема PostgreSQL на маркетплейс (`public` — Ozon, `wb` — WB) | Полная изоляция, SQL не меняется | Нестандартная модель: миграции по схемам, `search_path`, сравнение — через `UNION`-представления |
| **Общие таблицы + `marketplace`, составные ключи** | Нормализованная модель, одна цепочка миграций, сравнение маркетплейсов одним запросом | Разовая миграция ключей; каждый запрос обязан учитывать маркетплейс; аналитику нужно обновить до появления строк WB |

## Решение

Общие таблицы, в каждой — колонка `marketplace`, ссылка на справочник
`marketplaces (code, title)`.

- **Ключи товара составные.** Первичный ключ `products` и уникальный ключ
  `sku_panel` — `(marketplace, sku)`.
- **Целостность держит база.** `parse_runs` получает уникальный ключ
  `(run_id, marketplace)`. `price_history` и `parse_errors` ссылаются на
  `parse_runs` и на `products` составными внешними ключами. Записать
  наблюдение WB в прогон Ozon база не даст.
- **У `marketplace` нет значения по умолчанию.** Существующие строки получают
  `ozon` в момент миграции, потом DEFAULT снимается. Запись без маркетплейса
  падает с ошибкой, а не становится «ozon» молча.
- **Репозиторий привязан к маркетплейсу** при создании, и все его запросы
  фильтруют по нему: очередь panel, закрытие брошенных прогонов, блокировка
  прогона. Изоляцию проверяют тесты на настоящем PostgreSQL.
- **Представления** получают колонку `marketplace`, окна считаются по
  `PARTITION BY marketplace, sku`. Эквивалентность для Ozon проверяет эталон
  `tests/golden/views.json`: после миграции в нём должна появиться только
  колонка `marketplace` со значением `ozon`.
- **Регион сбора** записывается в `parse_runs.region`. У WB это явный `dest`,
  у Ozon — `NULL`: регион определяется по IP (см. #4).

## Последствия

- Запрос «медианная цена категории на Ozon и на WB по дням» пишется одним
  `GROUP BY marketplace`.
- Миграция меняет ключи боевых таблиц. Поэтому её проверяют на
  восстановленной копии боевой базы: выборки представлений по Ozon до и
  после миграции должны совпасть.
- ozon-market-analytics добавляет `marketplace` в staging-модели и в ключ
  `(marketplace, sku)` до того, как WB включат. После миграции, пока строк WB
  нет, его витрины остаются верными и без этого.
- Колонка `card_price` означает цену с платёжным инструментом маркетплейса
  (Ozon Карта). У WB она `NULL`: скидки WB Кошелька в ответе сайта нет.
