# ADR 0003. Адаптер маркетплейса — генератор итогов SKU, цикл сбора — в ядре

- Статус: принято, 10.10.2026
- Связано: [ADR 0001](0001-modular-monolith.md) — модульный монолит

## Контекст

Цикл прогона жил внутри парсера Ozon (`parse.run`). Там же находились
предохранитель (серия отказов), перезапуски браузера, учёт SKU, до которых не
дошла очередь, сохранение CSV и таблицы старого сценария. Для Wildberries
пришлось бы либо копировать всё это, либо делать WB частью модуля Ozon. Кроме
того, парсер Ozon импортировал старый сценарий (`legacy`), а это нарушало слои.

## Решение

Адаптер маркетплейса отдаёт итоги SKU генератором, всё остальное делает ядро:

```python
class MarketplaceAdapter(Protocol):
    def collect(self, skus: list) -> Generator[SkuOutcome, None, str | None]: ...
```

- **Адаптер** отвечает за транспорт: браузер или HTTP, прогрев, перезапуски,
  темп. Итоги отдаёт по порядку списка, по одному, сразу после разбора. Если
  не может продолжать (браузер падает раз за разом, не открылась сессия), то
  возвращает причину, и она достаётся SKU, до которых не дошла очередь.
- **Ядро** (`core.collect`) передаёт итог наблюдателю, ведёт предохранитель и
  на его срабатывании закрывает генератор. Закрытие генератора закрывает и
  транспорт адаптера (`finally` вокруг браузера). Ядро же отмечает недошедшие
  SKU (`not_processed` / `blocked` / `interrupted`), и они не теряются молча.
- **Наблюдатель** (`RunObserver`) решает, куда писать: конвейер пишет в
  PostgreSQL, старый сценарий — партиями в CSV / `ozon_products`. Несколько
  наблюдателей объединяет `Observers`.

## Почему генератор

- Ядро может остановить сбор в любой момент, не зная, как устроен транспорт.
- Итог каждого SKU записывается до разбора следующего, без буфера в памяти.
- Контракт проверяется без сайта и браузера: сценарный генератор в тестах —
  несколько строк (`tests/test_collect.py`, `tests/test_pipeline_run.py`).
- Батчи WB (100 товаров за запрос) ложатся сюда так же: адаптер получает
  батч и отдаёт итоги по одному.

## Последствия

- Конвейер и старый сценарий собирают одним циклом; правило «конвейер не
  опирается на `legacy`» соблюдается без исключений.
- Новый маркетплейс реализует один метод `collect`. Если ему нужно менять
  ядро, значит, контракт неверен, и его чинят до добавления маркетплейса.
- Темп запросов (`REQUEST_DELAY`, `PAGE_INTERVAL`) — забота адаптера: у
  каждого сайта свой антибот. Пороги предохранителя задаёт вызывающий.
- Тексты причин в `parse_errors.error_message` у недошедших SKU стали общими
  («сайт не отдавал данные N SKU подряд»); типы ошибок не изменились.
