# ADR 0001. Модульный монолит вместо отдельных проектов и оркестратора

- Статус: принято, 09.10.2026
- Контекст изменения: к Ozon добавляется Wildberries, дальше возможны другие
  маркетплейсы и сервисы

## Контекст

Конвейер собирает цены Ozon каждый день: discovery → panel → парсинг →
PostgreSQL, свой планировщик в Планировщике заданий Windows, бэкап и
оповещения. Следующий шаг — Wildberries, потом, возможно, другие источники,
и собирать их нужно вместе (возможно, параллельно).

Есть два пути:

1. Отдельный проект на каждый маркетплейс плюс оркестратор (Airflow,
   Prefect, Dagster), который ими управляет.
2. Один проект, в котором маркетплейсы — модули с общим контрактом.

Ограничения:

- одна машина (Windows, домашний IP) и один разработчик, проект — исследовательский;
- Ozon парсится только системным Chrome на хосте: в контейнере Ozon блокирует
  браузер (см. [operations.md](../operations.md#браузер-в-контейнере));
- у всех маркетплейсов общая база и общая инфраструктура: учёт прогонов,
  очередь panel, предохранитель, повторы после блокировки, миграции, бэкап,
  Telegram, пульс. Это большая часть кода.

## Решение

Один репозиторий, один пакет, одна база, один планировщик — **модульный
монолит**:

- ядро не знает о конкретных сайтах; каждый маркетплейс — модуль-адаптер с
  общим контрактом (сбор карточек по списку SKU, страницы выдачи для discovery);
- модули маркетплейсов не импортируют друг друга, правило зависимостей между
  слоями проверяется автоматически;
- каждый маркетплейс собирается в своём процессе, со своей блокировкой, своим
  пределом времени и своим повтором после блокировки. Маркетплейсы работают
  параллельно, а внутри маркетплейса запросы идут строго последовательно:
  антибот у сайтов независимый, а темп внутри сайта ограничен им;
- внешний оркестратор не вводится. Граница для него уже есть: CLI-команда на
  маркетплейс с кодами возврата (так устроен Airflow DAG).

## Почему не отдельные проекты с оркестратором

- **Общий код.** Учёт прогонов, предохранитель, миграции, бэкап и оповещения
  пришлось бы копировать или вынести в общую библиотеку с версиями и
  релизами. Для одного разработчика это работа без пользы.
- **Общая схема.** Два проекта, мигрирующие одну базу, конфликтуют, а с
  раздельными базами сравнивать маркетплейсы пришлось бы через ETL.
- **Оркестратор на этой машине.** Airflow не работает на Windows нативно.
  Оркестратор в Docker не запустит хостовый Chrome, без которого Ozon не
  собирается. И это ещё один сервис, который должен быть жив к ежедневному
  запуску.
- **Свой планировщик уже умеет нужное:** шаги отдельными процессами, жёсткие
  пределы времени, повторы после блокировки, бэкап, Telegram и пульс.

## Последствия

- Новый маркетплейс — это новый модуль, строка в реестре, секция в
  `config.yaml` и строка в таблице маркетплейсов. Если для него приходится
  менять ядро, значит, контракт неверен, и его исправляют до добавления.
- Сбой или зависание одного маркетплейса не задерживает и не ломает другой.
- Общая база и общий бэкап, одна точка развёртывания.
- Пока всё на одной машине, поломка этой машины останавливает сбор всех
  маркетплейсов.

## Когда пересмотреть

Решение стоит пересмотреть, если появится любое из этого:

- разные машины, IP или прокси для разных маркетплейсов;
- больше примерно пяти источников или источники на другом языке;
- несколько разработчиков с независимыми релизами;
- нужен интерфейс перезапуска прошлых дней (backfill) и SLA сверх Telegram и пульса.

Тогда — Prefect или Dagster, которые вызывают те же CLI-команды на
маркетплейс. Адаптеры переписывать не придётся.
