# Журнал живых проверок

Что проверено вручную на живом ozon.ru и реальных базах — с датой и
условиями. Автоматические тесты описаны в [development.md](development.md).
Новые записи добавляются сверху; цифры — только из фактических запусков.

## 06.10.2026 — вход не нужен, режим html

- **Сессия.** `cookies.json` от 25.09 загружен в Chrome без окна так же, как
  это делает парсер. После загрузки главной Ozon сбросил пользователя в гостя:
  `__Secure-user-id` = 0, в шапке «Войти», выданы новые гостевые токены.
  Значит, ежедневные прогоны 1200 из 1200 шли без входа, а проверка
  `ensure_session` (имена cookies и возраст файла) этого не видела. Гостевой
  браузер без cookies получает от API карточки HTTP 200 с ценой, ценой с
  картой, зачёркнутой ценой, наличием, рейтингом и отзывами. Итог:
  `schedule.ensure_session: false`, в `cookies.json` — пустое состояние.
- **Сверка режима html с API.** 100 случайных SKU panel, гость, Chrome без
  окна, пауза 3 с. У 92 SKU совпали все 13 сравниваемых полей: название, цена,
  цена с картой, зачёркнутая цена, скидка, наличие, рейтинг, отзывы, обложка,
  число фото и видео, цвет, материал. У 8 SKU в HTML нет названия: это товары
  не в продаже, API отдаёт им шаблонное имя («Смартфон», «Кофемолка») без
  цены. В режиме html такие SKU берутся из API. Разбор HTML занимает 0,42 с в
  среднем (p90 — 0,62 с), ожидание загрузки и запрос к API — 2,57 с (p90 —
  3,47 с). Ошибок нет. С `PAGE_SETTLE_MS` = 500 ни одного повтора из-за
  «context destroyed».
- **Benchmark в режиме html (run 12).** 50 из 50 SKU за 3 мин 20 с,
  14,99 SKU/мин, разбор 0,8 с на SKU плюс пауза 3 с. Вторая часть карточки по
  расписанию запрошена у 4 SKU, запасной путь через API понадобился 2 SKU.
  Раньше было 8,7–9,1 SKU/мин и 3,6 с на SKU. Пауза между товарами прежняя, но
  страниц в минуту стало больше: около 15 вместо 9.
- **`schedule --once`** с выключенной резервной копией: шага входа нет,
  `parse --missing-today` — «всё за сегодня собрано», код 0.

Не проверено: полный ежедневный прогон в режиме html; учащаются ли блокировки
при 15 страницах в минуту; команда `backup` на живой базе.

## 02.10.2026 — первый полный прогон panel

- **08:45 МСК, прогон по расписанию (run 5):** 302 SKU за 35 минут без единой
  антибот-проверки (вчера блокировка была на 186-м). В 09:20 у компьютера
  пропал интернет (`ERR_NAME_NOT_RESOLVED`); после 10 таких SKU подряд
  предохранитель остановил прогон. Статус `blocked`, хотя Ozon не блокировал:
  предохранитель не отличает пропажу сети от блокировки.
- **10:00 МСК, разовый повтор (run 6, задача `OzonParserOnce`):** **1200 из
  1200 SKU, 0 ошибок**, 2 ч 49 мин, 7,09 SKU/мин. Все карточки через API, ни
  одного 403, повтора или антибот-проверки. Разбор SKU: медиана 4,1 с, p90 —
  9,4 с, максимум — 18,4 с. Очередь «давно не обновлявшиеся первыми» сработала
  вживую: прогон начал с SKU, до которых не дошёл run 5.
- **Первая аналитика «день к дню»** (`v_price_daily`, 02.10 к 01.10): у 177
  SKU есть цена за оба дня, у 68 из них цена изменилась (55 вниз, 13 вверх,
  в среднем −0,83 % среди изменившихся). Смартфоны — 23 из 33, кофемашины —
  22 из 54, аксессуары для струнных — 15 из 46, чехлы — 8 из 44.
- После этого в `price_history` 1699 наблюдений по всем 1200 SKU panel.

Почему 01.10 Ozon заблокировал парсер на 186-м SKU, а 02.10 пропустил 1502
подряд (302 + 1200), по двум прогонам сказать нельзя: блокировка не
определяется одним числом запросов.

## 02.10.2026 — первый ежедневный прогон по расписанию на хосте

Прогон 01.10.2026 (задача `OzonParserDaily`, 18:00 МСК, Chrome без окна,
panel 1200 SKU):

- задача запустилась вовремя, сессия Ozon годна (`ensure_session` — 1 с);
- 18:00–18:21 МСК — 185 SKU в обычном темпе (~8,8 SKU/мин, 3–4 с на SKU),
  184 через API и 1 из HTML;
- в 18:21 на странице товара появилась антибот-проверка, которая не прошла за
  30 с, — и дальше не прошла ни одна страница. После 10 SKU подряд (по 3
  попытки, 17 минут) предохранитель остановил прогон в 18:38: статус
  `blocked`, 185 успешных, 10 `fetch_error`, 1005 не обработаны;
- проблема данных: при неизменном порядке обхода такие обрывы раз за разом
  давали бы историю только по первым ~185 SKU.

Исправлено по итогам (проверено тестами, на рабочей базе — очередь):
порядок обхода «дольше всех не обновлявшиеся первыми» (в очереди на 02.10
первыми идут 246 SKU, которые ещё ни разу не пробовали); непройденная проверка
не повторяется и при 3 подряд останавливает прогон; снимок экрана такой
проверки сохраняется в `logs/`.

## 29.09.2026 — конвейер и Docker

Живой ozon.ru, локальный PostgreSQL 16:

- разведка `data.ozon.ru` и листинга категорий ozon.ru — результаты в
  [discovery.md](discovery.md#источники);
- `migrate` на пустой базе создаёт 7 таблиц и 6 представлений, повторный
  запуск ничего не меняет;
- `discover` по четырём категориям: 80 SKU (по 8 top + 12 tail_random), 29
  запросов к листингу, около минуты. Один HTTP 403 снят повтором с повторным
  открытием категории;
- повторный `discover`: все категории пропущены за 0,4 с, без браузера,
  panel не изменилась;
- донабор: `panel_size` одной категории 20 → 30 — добавлено 4 top + 6 tail за
  4 запроса, исходные 20 строк не изменились (сверено по хэшу);
- `parse`, `benchmark`, `schedule --once` (последний — с отключённым шагом
  сессии): все SKU разобраны и записаны, `parse_runs` заполнен, история по
  одним и тем же SKU растёт от прогона к прогону (цифры — в
  [performance.md](performance.md));
- `parse_ozon.py --file data/panel_skus.csv --limit 2`: старый парсер читает
  выгрузку panel, CSV — прежние 12 полей;
- представления `v_price_daily`, `v_price_volatility`, `v_category_daily`,
  `v_panel_summary` возвращают данные по накопленной истории: 223 наблюдения
  по 90 SKU за 4 прогона. Вся живая история тогда укладывалась в один день, и
  за ~20 минут между прогонами цены не менялись. Поэтому изменение к прошлому
  дню (`prev_price`, `price_change`) проверено тестом на PostgreSQL с данными
  за два дня, а не на живых данных.

Docker Desktop на Windows, по логам в `logs/`:

- `docker compose up -d`: образ собрался, миграции применились к базе в
  контейнере `postgres`, планировщик запустился с расписанием;
- `discover` в контейнере с полными размерами и паузой 2 с: `phone_cases`
  собрана (300 SKU, 110 запросов), остальные три категории получили HTTP 403
  на всех попытках. Discovery переделан (темп, выжидание при отказе,
  сохранение частичного результата). С новой версией примерно через 25 минут
  после блокировки проверен донабор `smartphones` (+20 SKU) на локальной
  базе: 6 запросов с интервалами 4–7 с, ни одного 403;
- второй `discover` (пауза 5 с, одна сессия на весь прогон): `smartphones`
  собрана целиком (300 SKU, 79 страниц), `coffee_machines` сразу получила 403,
  выжидание 10 с → 1 → 3 → 5 мин в той же сессии не помогло, discovery
  остановился, сохранив собранное. После этого каждая категория обходится в
  своей сессии браузера, повтор при отказе — тоже в новой. Короткая проверка
  на локальной базе: две категории подряд (`coffee_machines` →
  `string_accessories`) по 2 запроса, каждая в своей сессии, 403 не было.
  Полный сбор — в записи за 30.09.

  парсер с этой сессией разобрал обе карточки;

  Airflow: со свежей сессией — выход без браузера; с протухшей (лимит 0 дней)

  отправки. Для тестового аккаунта Ozon предложил подтверждение QR-кодом или
  звонком — такой случай скрипт распознаёт и останавливается с объяснением.
