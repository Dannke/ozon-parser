## Поток данных

```text
 config.yaml: категории, panel_size, top_ratio, расписание
        |
        v
 DISCOVERY                       python -m ozon_parser discover
   листинг категории ozon.ru (Playwright + внутренний API фронтенда)
   или отчёт data.ozon.ru «Аналитика товаров» (опционально)
   SKU из URL карточки -> дедупликация -> top + tail_random
        |
        v
 SKU PANEL                       таблица sku_panel (+ data/panel_skus.csv)
        |
        v
 DAILY PARSING                   python -m ozon_parser parse
   ежедневно: scripts/run_daily.ps1 (Планировщик заданий Windows)
   каждый SKU: открыть карточку -> JSON API -> запасной путь JSON в HTML
        |  запись сразу после разбора SKU
        v
 POSTGRESQL
   parse_runs · products · price_history · parse_errors · discovery_runs
        |
        v
 HISTORICAL DATA
   v_price_daily · v_price_latest · v_price_volatility · v_category_daily
```

Этапы связаны только данными: discovery пишет `sku_panel`, парсер её читает.
Парсер можно запустить и по обычному файлу со списком SKU, а discovery ничего
не знает о разборе карточек.

Парсер карточек один на оба сценария: `parse.run()` вызывают и старый
`parse_ozon.py` (CSV / `ozon_products`), и конвейер. Конвейер подключается к
нему через хуки `RunObserver`: итог каждого SKU пишется в PostgreSQL сразу
после разбора, до перехода к следующему.

## Как устроен парсинг карточки

**Почему браузер, а не `requests`.** Ozon закрыт антибот-защитой. Запрос из
`requests.Session` даже с действующими cookies из `cookies.json` получает
HTTP 403 и на API, и на HTML-страницу: защита проверяет, что запрос сделал
настоящий браузер (JS-проверка, отпечаток TLS). Поэтому сессия поднимается в
Playwright. Cookies из файла загружаются в контекст браузера так же, как в
`requests.Session` загружался бы cookie jar, а запросы к API выполняются из
страницы и несут эти cookies.

Данные карточки доступны двумя путями, и оба разбираются одним кодом
(`extract.py`).

**Внутренний JSON API**, из которого фронтенд собирает страницу:

```text
/api/entrypoint-api.bx/page/json/v2?url=/product/<sku>/
```

Ответ — объект с `widgetStates`: состояния виджетов в виде JSON-строк. Две
особенности, выясненные на живых карточках:

1. Карточка отдаётся двумя запросами. Описание и полный список характеристик
   лежат во второй части (`layout_page_index=2`), без неё `art_set` и
   `has_rich_content` неизвестны.
2. Запрос проходит только из вкладки с открытой карточкой, иначе Ozon отвечает
   403. Поэтому парсер сначала открывает страницу товара и даёт ей устояться
   (`PAGE_SETTLE_MS`).

**JSON, встроенный в HTML карточки.** Сервер отдаёт первую часть страницы уже
отрисованной. Каждый виджет в ней — `<div id="state-webPrice-…" data-state='{…}'>`
с тем же JSON, что и в `widgetStates`. Рядом лежит блок
`<script type="application/ld+json">` со schema.org Product. Оба извлекаются
стандартным `html.parser`, недостающие поля добираются из JSON-LD. В HTML есть
всё, кроме описания и полных характеристик.

**Порядок источников** задаёт режим (`parse.ParseOptions`):

| Режим | Кто использует | Порядок |
| ----- | -------------- | ------- |
| `api` | `parse_ozon.py` (старый сценарий) | Открыть карточку, дать ей устояться, обе части из API; если API не ответил — HTML (`source = html`) |
| `html` | конвейер (`parser.price_source: html`) | Открыть карточку и сразу разобрать HTML, без запросов к API и без ожидания полной загрузки. Если в HTML нет названия или цены — путь `api` |

Вторая часть карточки (описание, полные характеристики) конвейеру нужна
редко: у SKU без описания — в каждом прогоне, у остальных — раз в
`parser.details_refresh_days` дней, каждый день у своей части panel
(`pipeline.details_schedule`). В режиме `html` за ней парсер ходит в API из
той же вкладки. Получила ли запись вторую часть, отмечает поле `details`. Без
неё описание и характеристики в `products` не перезаписываются (см.
[data-model.md](data-model.md#решения-по-схеме)).

06.10.2026 режим `html` сверен с API на живых карточках (см.
[verification-log.md](verification-log.md)), но сейчас включён `api`.

**Темп** задаёт не скорость разбора, а частота открытия страниц. После
каждого товара парсер ждёт `REQUEST_DELAY`. Кроме того, перед каждым
`page.goto` (`parse.wait_page_slot`) он ждёт, пока с открытия предыдущей
страницы пройдёт `PAGE_INTERVAL`. Предел действует при повторах SKU и при
прогреве после перезапуска браузера. 07.10.2026 разбор из HTML без этого
предела ускорил обход до ~14 карточек в минуту при той же паузе 3 с, и на
14-й минуте пришла капча. При ~9 в минуту прогоны идут часами. С пределом
режим `html` даёт меньше запросов к API, но не больше страниц в минуту.

Rich-описание у Ozon бывает двух видов, и оба учитываются: структурный
`richAnnotationJson` с блоками (картинки, таблицы, списки) и HTML-текст в
`richAnnotation`.

Какие поля собираются и откуда — в [data-model.md](data-model.md#поля-карточки).

## Обработка ошибок

Обрабатываются и логируются:

- нет доступа к почте, письмо не пришло за таймаут, код не распознан в письме;
- старое письмо с предыдущим кодом — отсекается по времени запроса;
- антибот-проверка — ожидание её прохождения, отказ по таймауту;
- не найдены кнопка входа, поле почты, телефона или кода (изменилась вёрстка);
- маска поля исказила номер — код не запрашивается;
- Ozon выбрал подтверждение через QR-код или звонок — остановка с объяснением;
- таймаут загрузки, сетевые сбои — повторы (`MAX_RETRIES`);
- API карточки недоступен — данные из JSON в HTML;
- несуществующий SKU (HTTP 404) — без бессмысленных повторов;
- браузер упал или закрыт посреди списка — перезапуск (`MAX_BROWSER_RESTARTS`),
  SKU, на котором он упал, обрабатывается заново;
- антибот-проверка на странице товара не прошла за `CHALLENGE_TIMEOUT` — SKU
  не повторяется (это блокировка, а не сбой), снимок экрана — в `logs/`;
- серия SKU подряд без данных (кроме 404) — остановка прогона: 3 с
  непройденной проверкой или 10 по любой причине. Так выглядит блокировка
  Ozon (см. [operations.md](operations.md#предохранитель));
- временные сбои Gmail API (429, 5xx) — экспоненциальная пауза;
- прерывание по Ctrl+C — собранное сохраняется;
- недоступная БД или недоступный CSV — одно не блокирует другое: при
  недоступной базе CSV всё равно пишется, а ошибка базы потом поднимается
  наверх, чтобы прогон не выглядел успешным.

В конвейере (`python -m ozon_parser parse`) дополнительно:

- каждый SKU пишется в PostgreSQL сразу после разбора, до следующего SKU;
  проблемный SKU не останавливает прогон, его причина попадает в
  `parse_errors` вместе с числом попыток (типы — в
  [data-model.md](data-model.md#таблицы));
- SKU, до которых не дошла очередь (браузер падал чаще
  `MAX_BROWSER_RESTARTS`, прогон прерван или остановлен предохранителем, не
  открылся файл сессии), тоже попадают в `parse_errors`, а не пропадают молча.
  Очередь следующего прогона начинается с дольше всех не обновлявшихся SKU,
  так что они не теряются;
- обрыв соединения с PostgreSQL — одна повторная попытка на новом соединении;
  если запись всё равно не прошла, SKU считается ошибкой `storage_error`.
  Ошибка первого подключения (неверный пароль, база не запущена) не
  повторяется и выводится сразу;
- второй одновременный прогон отказывается стартовать (advisory lock), а
  прогон, брошенный упавшим процессом, помечается `interrupted`;
- в discovery отказ Ozon (403 / 429 / антибот-заглушка) — выжидание по
  `block_backoff` с повтором в новой сессии браузера. Если отказ не снялся,
  найденное сохраняется, оставшиеся категории не запускаются (статус
  `stopped`), и повторный `discover` доберёт остальное. Обычный сбой страницы
  — короткие повторы и пропуск страницы. Итог каждой категории пишется в
  `discovery_runs`. Если хоть одна категория не собрана до `panel_size`,
  `discover` возвращает код 1.

Пустой прогон не считается успешным: парсер возвращает 1, а CSV старого
сценария перезаписывается одним заголовком, чтобы не выдать снимок прошлого
запуска за сегодняшний.

## Совместимость со старым сценарием

- `python parse_ozon.py --file skus.txt` работает как раньше: CSV
  `data/products.csv`, а при `--storage postgres` — таблица `ozon_products`.
- `discover` выгружает panel в `data/panel_skus.csv` (столбец `sku`), и этот
  файл принимает старый парсер: `python parse_ozon.py --file data/panel_skus.csv`.
  Строка заголовка `sku` в файле SKU пропускается.
- Конвейер пишет в свои таблицы и в CSV `data/panel_products.csv`, чтобы не
  перезаписывать снимок старого сценария.
- Новые поля карточки (`card_price`, `old_price`, `discount_pct`,
  `is_available`) в CSV и `ozon_products` не попадают: там по-прежнему ровно
  12 полей задания.

Старый сценарий целиком — в [legacy.md](legacy.md).
