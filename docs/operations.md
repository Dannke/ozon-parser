## Ежедневный запуск

Каждый день в `schedule.daily_at` из `config.yaml` (сейчас 08:45 по Москве)
выполняются шаги отдельными процессами — это команда
`python -m ozon_parser schedule --once`:

```text
[ensure_session]  только если schedule.ensure_session: true (сейчас выключен)
    -> parse --kind daily --missing-today
         -> активные SKU из sku_panel, у которых за сегодня ещё нет наблюдения
         -> парсинг, запись каждого SKU в products / price_history
         -> parse_runs (итог и скорость), parse_errors (причины)
    -> статус blocked? через 3 ч ещё раз те же шаги (см. ниже)
    -> backup: копия базы в backups/ (если backup.enabled)
    -> оповещение: пульс мониторинга, при проблемах - Telegram (если настроены)
```

Отдельные процессы нужны для изоляции: браузер и драйвер Playwright умирают
вместе с прогоном и не копят память от ночи к ночи. Прогоны идут строго по
очереди, у ежедневного прогона вместе с повтором есть жёсткий предел
длительности (`schedule.parse_timeout_hours`, 10 ч).

Вход в аккаунт Ozon прогону не нужен: карточки открываются без него, а
сессия из `cookies.json` при загрузке страницы всё равно оказывалась гостевой
(проверено 06.10.2026). Поэтому шаг `ensure_session` выключен. Если его
включить, а войти не удастся, парсинг всё равно запустится.

Порядок SKU в прогоне — **дольше всех не обновлявшиеся первыми**: сначала
SKU, которые ещё ни разу не пробовали разобрать, затем по давности последней
попытки (SKU, до которых прогон просто не дошёл, попыткой не считаются). При
равенстве — `md5(sku)`, то есть вперемешку между категориями. Так даже
прогоны, которые обрываются на середине (01.10.2026 Ozon заблокировал парсер
на 186-м SKU из 1200), за несколько дней обходят всю panel, а не одни и те же
первые сотни товаров.

Прогон panel из 1200 SKU идёт около 2,3 ч (см. [performance.md](performance.md)).
День наблюдения в аналитике считается по Москве, поэтому прогон должен
закончиться до полуночи; если panel вырастет, время запуска стоит сдвинуть
раньше.

### Планировщик заданий Windows

Рабочий вариант сейчас: парсинг на хосте в Google Chrome, база — в Docker.

```bash
powershell -ExecutionPolicy Bypass -File scripts\register_windows_task.ps1
```

Скрипт регистрирует задачу `OzonParserDaily`, которая запускает
`scripts/run_daily.ps1` (Chrome без окна, `HEADLESS=1`). Особенности:

- **Время.** Берётся из `config.yaml` и переводится в местное время Windows:
  18:00 МСК на машине с UTC+7 — это 22:00. После смены `daily_at` или
  часового пояса Windows скрипт регистрации нужно запустить ещё раз.
- **Учётная запись.** Задача выполняется от текущего пользователя, только
  когда он вошёл в систему. Пароль Windows не нужен и не сохраняется.
- **Пропущенное время.** Если компьютер был выключен, задача запустится при
  первой возможности.
- **Второй экземпляр** не стартует, пока идёт первый. Лимит задачи Windows —
  `parse_timeout_hours` + 1 ч (11 ч): прогон завершается сам раньше, лимит —
  страховка от зависания.
- **Проверить или удалить:**
  `Get-ScheduledTask -TaskName OzonParserDaily | Get-ScheduledTaskInfo`,
  `Unregister-ScheduledTask -TaskName OzonParserDaily`.

Условия для прогона: компьютер включён и не уходит в сон всё время прогона
(Параметры → Система → Питание), вы вошли в систему, Docker Desktop запущен
(в нём база).

### Контейнерный планировщик

`python -m ozon_parser schedule` — простой цикл, который ждёт `daily_at` и
выполняет те же шаги. В docker-compose он лежит под профилем и по умолчанию
не стартует: в контейнере Ozon блокирует браузер на карточках (см.
[Браузер в контейнере](#браузер-в-контейнере)). Включить, когда это будет
исправлено:

```bash
docker compose --profile container-scheduler up -d
```

### Airflow

Airflow DAG (`dags/ozon_parser_dag.py`) обслуживает старый сценарий (см.
[legacy.md](legacy.md#airflow)). Чтобы перевести его на panel, достаточно
заменить команду задачи `parse_products` на
`python -m ozon_parser parse --kind daily`.

### Повтор после блокировки

Если прогон остановил [предохранитель](#предохранитель) (статус `blocked`,
код возврата `parse` — 3), ежедневная задача не завершается, а ждёт
`schedule.block_retry_delay_hours` (3 ч) и выполняет шаги ещё раз:

- повтор берёт только SKU, у которых **за сегодня** (день по
  `schedule.timezone`) ещё нет успешного наблюдения (`parse --missing-today`).
  Уже собранные не парсятся второй раз — меньше запросов к Ozon;
- повторов не больше `schedule.block_retries` (1);
- повтор не начинается, если до конца `parse_timeout_hours` (от старта
  задачи) останется меньше часа. Тогда недостающие SKU возьмёт первыми
  следующий ежедневный прогон;
- прочие неудачи (`failed`, `partial` ниже `min_success_rate`, таймаут) не
  повторяются: повтор через 3 часа их не исправит;
- в `logs/scheduler.log` — строка «Прогон остановлен блокировкой Ozon -
  повтор 1 из 1 в 12:24 MSK», в `runs` — отдельный прогон `daily` с
  `total` = числу недостающих SKU.

Повод — 05.10.2026: капча остановила прогон на 348-м SKU из 1200. Капча там
была интерактивной («Сопоставьте пазл, двигая ползунок»): сама она не
проходит, а решать её автоматически парсер не будет. Остаётся переждать.
Помогает ли пауза в 3 часа, станет видно по первым срабатываниям.

Догнать вручную в тот же день:

```bash
python -m ozon_parser parse --kind daily --missing-today
```

## Резервные копии

Вся история цен лежит в томе Docker `pgdata`. `docker compose down -v` или
сброс Docker Desktop стёрли бы её целиком, поэтому после ежедневного прогона
(и после повтора, если он был) снимается копия базы:

- `pg_dump` в формате custom запускается внутри контейнера `postgres`
  (`docker compose exec`): на хосте клиента PostgreSQL нет;
- копия пишется во временный файл и проверяется: это архив `pg_dump`, а
  `pg_restore --list` находит в оглавлении данные `price_history`. Только
  после этого она встаёт на место — `backups/ozon-ГГГГ-ММ-ДД.dump`;
- хранятся последние `backup.keep` копий (14); повторная копия за день
  заменяет предыдущую;
- копия снимается и после неудачного прогона: собранное за день уже в базе;
- её сбой не меняет код возврата прогона, но попадает в оповещение.

Вручную:

```bash
python -m ozon_parser backup
```

Каталог задаётся `backup.dir`. Надёжнее держать копии на другом диске или в
папке, которая синхронизируется с облаком: в них только данные о товарах.

Восстановление — в новую пустую базу, чтобы не смешать с текущей. Копию
сначала кладём в контейнер: передавать архив через конвейер PowerShell
нельзя, он портит двоичные данные.

```bash
docker compose cp backups/ozon-2026-10-06.dump postgres:/tmp/restore.dump
```

```bash
docker compose exec -T postgres createdb -U ozon ozon_restored
```

```bash
docker compose exec -T postgres pg_restore -U ozon -d ozon_restored --no-owner /tmp/restore.dump
```

Проверить восстановленную базу можно, указав её в `PG_DSN` и выполнив
`python -m ozon_parser runs`.

## Оповещения

Без оповещений о сбое можно узнать только из логов. После каждого ежедневного
прогона уходят два сигнала, если они настроены в `.env`:

- **пульс** (`HEALTHCHECK_URL`, например бесплатный healthchecks.io): после
  успешного прогона открывается этот адрес, после неудачного — адрес + `/fail`.
  В сервисе задаётся расписание (раз в сутки, запас 4–6 ч). Если пульса нет
  совсем — компьютер был выключен или спал, — сервис предупредит сам;
- **Telegram** (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`): сообщение только о
  проблемах — прогон не удался, Ozon остановил его капчей (`blocked`), копия
  базы не снята. В сообщении — итог последнего прогона из `parse_runs`.

Как получить значения: бот создаётся у @BotFather, он выдаёт токен. Напишите
боту любое сообщение и откройте
`https://api.telegram.org/bot<токен>/getUpdates` — `chat.id` в ответе и есть
`TELEGRAM_CHAT_ID`. Адрес пульса выдаёт сервис мониторинга при создании
проверки.

Оповещение — вспомогательный шаг: его сбой пишется в `logs/notify.log` и не
меняет итог прогона. Токен бота в лог не попадает. Тесты оповещения не
отправляют, даже если они настроены в `.env`.

## Мониторинг

```bash
python -m ozon_parser runs
```

Показывает последние прогоны (время — в часовом поясе расписания) и объём
истории. Как читать статус прогона:

| Статус        | Что значит                                                        | Что делать |
| ------------- | ----------------------------------------------------------------- | ---------- |
| `success`     | Все SKU разобраны                                                 | — |
| `partial`     | Часть SKU с ошибками                                              | Посмотреть `parse_errors` |
| `failed`      | Ни одного успешного SKU                                           | Логи, см. «Типовые проблемы» |
| `blocked`     | Сработал предохранитель: Ozon подряд не отдавал данные            | Ждать автоповтора через 3 ч; логи |
| `interrupted` | Процесс оборвался: компьютер уснул или выключился, Ctrl+C          | Проверить настройки питания |
| `running`     | Идёт сейчас (или процесс убит; пометится при следующем прогоне)    | — |

Ориентир для полного ежедневного прогона: 1200 успешных SKU примерно за
3 часа, около 7 SKU/мин (02.10.2026 — 2 ч 49 мин). Если Ozon заблокирует
парсер (01.10.2026 — на 186-м SKU, 05.10.2026 — на 349-м, см.
[limitations.md](limitations.md#эксплуатация)), исход — `blocked` с частью SKU,
а через 3 часа — [повтор](#повтор-после-блокировки) по недостающим.

Прогон оборвался из-за выключения компьютера — догоните его вручную
(`python -m ozon_parser parse --kind daily --missing-today`) или разовой
задачей Windows с тем же действием, что у `OzonParserDaily`. Состав panel — `python -m ozon_parser panel`. Для
аналитики — представления из [data-model.md](data-model.md).

## Доступ для аналитики: роль только для чтения

Для BI-инструментов (DataLens, DBeaver, Jupyter) в базе заведена роль
`analyst`: читает все таблицы и представления схемы `public`, ничего в них не
меняет, а свои представления и таблицы создаёт в собственной схеме
`analytics`. Парсер по-прежнему работает под `ozon`.

Роль создаётся один раз вручную (пароль не хранится в репозитории). Повторить
нужно, только если том `pgdata` пересоздан:

```bash
docker compose exec -T postgres psql -U ozon -d ozon -v ON_ERROR_STOP=1
```

```sql
BEGIN;
CREATE ROLE analyst LOGIN PASSWORD '<пароль>';
GRANT CONNECT ON DATABASE ozon TO analyst;
GRANT USAGE ON SCHEMA public TO analyst;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO analyst;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO analyst;
CREATE SCHEMA analytics AUTHORIZATION analyst;
COMMIT;
```

- `ALTER DEFAULT PRIVILEGES` действует на объекты, которые создаёт `ozon`, —
  то есть и на таблицы и представления будущих миграций: доступ к ним
  появится сам.
- Подключение: хост `127.0.0.1`, порт `5433`, база `ozon`, пользователь
  `analyst`. База слушает только localhost этой машины.
- Проверено 02.10.2026: чтение `price_history` и `v_price_daily` работает;
  `INSERT` / `DELETE` в таблицы `public` и `CREATE TABLE` в `public` —
  `permission denied`; представление в `analytics` создаётся; новая таблица,
  созданная `ozon`, сразу читается под `analyst`.

## Логи

Логи пишутся в консоль и в `logs/<модуль>.log` с ротацией (10 МБ, 5 файлов).
Ключевые события — одной строкой с маркером, их легко искать. Строки ниже
взяты из прогонов 29.09.2026; строка `SKU ERROR` — шаблон формата:

```text
DISCOVERY START categories=phone_cases,smartphones,... rebuild=False seed=...
CATEGORY START category=phone_cases source=ozon_listing panel_size=20 need_top=8 need_tail=12
SKU DISCOVERED category=phone_cases page=132 group=tail found=8
PANEL CREATED added=80 categories=4
PARSER START run_id=2 kind=benchmark source=panel total=50 request_delay=3.0
SKU SUCCESS run_id=2 sku=1410034443 price=269.0 old_price=700.0 available=True seconds=3.3
SKU ERROR run_id=<id> sku=<sku> type=<not_found|fetch_error|...> attempts=<n> message=<текст>
PARSER FINISHED run_id=2 status=success success=50 errors=0 duration=346s speed=8.66 SKU/min
```

| Файл                    | Что в нём                                              |
| ----------------------- | ------------------------------------------------------ |
| `logs/scheduler.log`    | Запуски ежедневной задачи, шаги и коды возврата        |
| `logs/pipeline.log`     | `PARSER START/FINISHED`, `SKU SUCCESS/ERROR`           |
| `logs/parse_ozon.log`   | Подробный лог парсера: каждая карточка, повторы        |
| `logs/discovery.log`    | Discovery по категориям и страницам                    |
| `logs/browser.log`      | Запуск браузера, антибот-проверки; текст непройденных  |
| `logs/challenge-*.png`  | Снимки экрана непройденных антибот-проверок            |
| `logs/warehouse.log`    | Миграции, соединение с PostgreSQL                      |
| `logs/backup.log`       | Резервные копии базы: файл, размер, сколько старых удалено |
| `logs/notify.log`       | Отправка пульса и сообщений в Telegram                 |
| `logs/get_cookies.log`, `logs/gmail.log`, `logs/session.log` | Вход и сессия Ozon |

Контейнер пишет в ту же папку `logs/` (она подключена томом). Время в строках
от контейнера — московское, от процессов на хосте — местное время Windows;
`python -m ozon_parser runs` показывает всё в часовом поясе расписания.

## Предохранитель

Прогон останавливается сам, если Ozon подряд не отдаёт данные:

- **3 SKU подряд с непройденной антибот-проверкой** (`MAX_CONSECUTIVE_CHALLENGES`)
  — самый явный признак блокировки. Такой SKU не повторяется (каждая попытка
  стоила бы ещё 30 с ожидания), ошибка пишется с типом `antibot`. Остановка
  наступает примерно через 2 минуты после начала блокировки;
- **10 SKU подряд без данных по любой причине** (`MAX_CONSECUTIVE_FAILURES`);
- ответ «товара нет» (404) серию не продолжает, успешный SKU её сбрасывает;
- прогон получает статус `blocked`, необработанные SKU пишутся в
  `parse_errors` с типом `blocked`, код возврата — 3. Ежедневная задача по
  этому коду через 3 часа [повторяет](#повтор-после-блокировки) прогон по
  недостающим SKU; благодаря порядку обхода они в любом случае будут первыми
  в следующем прогоне.

При непройденной проверке в `logs/` сохраняется снимок экрана
`challenge-<дата-время>.png` (не больше 3 за прогон и 20 всего), а в
`logs/browser.log` — адрес, заголовок и видимый текст страницы. По ним видно,
что именно показал Ozon: капчу, бесконечную проверку или заглушку.

Поводы: прогон 30.09.2026 в контейнере 5 часов делал по 3 попытки на каждый
товар; прогон 01.10.2026 на хосте после блокировки ещё 17 минут повторял
непройденные проверки, прежде чем сработал порог в 10 SKU.

`0` в `.env` отключает соответствующий порог.

## Docker

```bash
docker compose up -d
```

поднимает только PostgreSQL на `127.0.0.1:5433` (том `pgdata` сохраняет данные
между перезапусками). Образ парсера используется для разовых команд, например
discover:

```bash
docker compose run --rm parser python -m ozon_parser discover
```

- `config.yaml` подключён в контейнер как файл: правки действуют со следующей
  команды.
- Код копируется в образ при сборке — после обновления кода:
  `docker compose build parser`.
- `cookies.json`, `token.json` и `credentials.json` подключаются томами и
  должны существовать до первого запуска: отсутствующий файл Docker подменит
  пустым каталогом с тем же именем.
- Внутри compose парсер подключается к базе сам (`PG_DSN` собирается в
  `docker-compose.yml`), браузер — встроенный Chromium без окна.

### Браузер в контейнере

30.09.2026 первый ежедневный прогон шёл в контейнере и почти целиком провалился:

- встроенный Chromium от Playwright (headless, Linux) получал **HTTP 403 от
  API каждой карточки**, на каждой странице показывалась антибот-проверка;
- в HTML за первым товаром данных тоже не было;
- за 5 ч 19 мин: 1 успешный SKU, 953 ошибки `fetch_error`; в 23:19 процесс
  оборвался вместе с остановкой компьютера;
- повторный тест в контейнере 01.10 — 1 из 3;
- те же SKU с того же IP в Google Chrome на хосте — 3 из 3 через API.

Вероятная причина — отпечаток браузера: headless-сборка Chromium и
User-Agent «Windows» на Linux. Возможное исправление: настоящий Google Chrome
в образе, User-Agent под Linux, при необходимости Chrome с окном на
виртуальном экране (Xvfb). Это пока не сделано и не проверено. Discovery
(листинг категорий) в контейнере при этом работает.

## Типовые проблемы

| Симптом | Причина и решение |
| ------- | ----------------- |
| `password authentication failed for user "user"` | В `PG_DSN` не тот пользователь. База из docker-compose создаётся с `POSTGRES_USER` (по умолчанию `ozon`): `PG_DSN=postgresql://ozon:<пароль>@127.0.0.1:5433/ozon` |
| `connection to server at "localhost" (::1) ... Connection refused` | Безвредно: порт открыт только на `127.0.0.1`, драйвер сначала пробует IPv6. Чтобы не видеть строку, укажите в `PG_DSN` `127.0.0.1` |
| Сменили `POSTGRES_PASSWORD`, а пароль базы прежний | Пароль задаётся только при первом создании тома `pgdata`; меняйте его в самой базе (`ALTER USER`) |
| `discover` пишет `STOPPED` | Ozon ограничил запросы. Найденное сохранено; запустите `discover` снова через 30–60 минут |
| Прогон в статусе `interrupted` | Компьютер уснул или выключился во время прогона. Отключите сон на время прогона |
| Прогон в статусе `blocked` | Ozon перестал отдавать карточки. Не перезапускайте сразу: через 3 часа задача сама повторит прогон по недостающим SKU, а что не успеет — возьмёт первым следующий прогон. Что показал Ozon — на снимках `logs/challenge-*.png` и в `logs/browser.log`. Интерактивную капчу (пазл с ползунком) парсер не решает и решать не будет |
| `parse` в контейнере: почти всё `fetch_error`, в логе `API ответил HTTP 403` | Ozon блокирует браузер контейнера, см. [Браузер в контейнере](#браузер-в-контейнере). Парсите на хосте |
| data.ozon.ru просит войти заново | Сессия устарела: `python get_cookies.py --force`. Нужно только для источника `data_ozon`, парсингу карточек сессия не нужна |
| `Резервная копия не создана: не найден docker` | Не запущен Docker Desktop или `docker` нет в `PATH` задачи Windows. Копию можно снять позже: `python -m ozon_parser backup` |
| `pg_restore не читает копию` | Архив повреждён или пуст; прежние копии не тронуты. Подробности — в `logs/backup.log` |
| Chromium на Windows: `side-by-side configuration is incorrect` | Укажите системный браузер: `BROWSER_CHANNEL=chrome` или `msedge` |
| Вместо `cookies.json` в папке проекта появился каталог | Docker смонтировал отсутствующий файл. Удалите каталог и выполните `python get_cookies.py` |
| Новой строки в `runs` нет | Задача не запускалась: `logs/scheduler.log`, статус задачи `OzonParserDaily` в Планировщике заданий |

## Секреты

`.env`, `credentials.json`, `token.json` и `cookies.json` содержат секреты и
перечислены в `.gitignore`:

- `token.json` — доступ на чтение всей почты. Пока вход не используется,
  живой токен можно отозвать в аккаунте Google («Безопасность» → сторонние
  приложения) и удалить файл; при следующем `get_cookies.py` окно согласия
  откроется снова;
- `cookies.json` — сессия Ozon, если вход выполнен (сейчас там пустое
  состояние);
- `TELEGRAM_BOT_TOKEN` в `.env` — управление ботом оповещений.

Не передавайте их ни в репозитории, ни в архиве с проектом. `token.json` и
`cookies.json` создаются с правами `0600`. На Windows POSIX-права не
действуют, и доступ там можно ограничить только через ACL.

В Docker-образ секреты не попадают (`.dockerignore`): docker-compose
подключает их томами при запуске, а пароль PostgreSQL берёт из `.env`
(`POSTGRES_PASSWORD`). В Python-коде и `config.yaml` учётных данных нет.
База слушает только `127.0.0.1`; на сервере используйте стойкий пароль.
