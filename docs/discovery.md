## Источники

### data.ozon.ru: проверено, подходит частично

Сначала проверен официальный сервис Ozon для продавцов — `data.ozon.ru`
(«Что продавать на Ozon»), куда проект и так входит в `get_cookies.py`.
Результаты на живом сервисе 29.09.2026:

- раздел «Аналитика товаров» (`/app/bestsellers`) получает данные запросом
  `POST /p-api/exa-auth/analytics_what_to_sell/what_to_sell` с телом
  `{"filter": {"categories": [...], "brandIds": []}, "limit": "50",
  "offset": "0", "sort": {"attribute": "sum_gmv", "order": "desc"}}`;
- в ответе есть `sku`, ссылка на карточку, категория, продажи и выручка
  за 28 дней;
- `limit` не больше 100 («limit must be ... less than or equal to 100»);
- `offset` меньше 1000 («offset limit exceeded»), `totals` = 1000. Значит, по
  любому фильтру доступно только окно из 1000 строк, отсортированных по
  метрике. Сортировка `asc` отдаёт другой край (товары с 1 продажей), а
  середину распределения получить нельзя;
- нужна авторизованная сессия `data.ozon.ru`. Во время разведки сессия,
  сохранённая в `cookies.json`, через несколько запусков браузера
  перестала приниматься (редирект на вход Ozon ID): токены обновляются на
  лету, и без сохранения нового состояния файл устаревает. Поэтому discovery
  сохраняет обновлённую сессию после удачной работы с `data.ozon.ru`;
- фильтр по категории — список id узлов дерева `get_seller_tree_v2`: для
  уровней 1–2 это `descriptionCategoryId`, для 3-го — `descriptionTypeId`
  (например, «Смартфон» — `95139`). Формат взят из кода фронтенда
  `data.ozon.ru`. **Вживую запрос с фильтром не проверен:** к этому моменту
  сессия уже была недействительна.

Вывод: источник реальный и дешёвый (10 запросов на 1000 SKU), но это выборка
из топ-1000 категории по продажам, и «хвост» в нём — хвост лидеров, а не
категории. Он реализован как опциональный источник `source: data_ozon`
(пример закомментирован в `config.yaml`). По умолчанию используется листинг
ozon.ru.

### Листинг категории ozon.ru (по умолчанию)

Страница категории открывается в Playwright: так проходит антибот-проверка и
подхватываются cookies. Страницы выдачи запрашиваются у того же внутреннего
API, которым пользуется фронтенд:

```text
/api/entrypoint-api.bx/page/json/v2?url=/category/smartfony-15502/?page=N
```

Что выяснено на живом сайте (29.09.2026):

- товары лежат в виджете `tileGridDesktop`, **по 8 на страницу**. Страницы
  идут подряд без пересечений; HTML-страница `?page=N` показывает блоки N и
  N+1. При повторном запросе той же страницы 7–8 товаров из 8 совпадают;
- выдача обрывается на **646–684-й странице** (~5200–5400 позиций) во всех
  четырёх категориях, включая нишевую: похоже, Ozon ограничивает глубину
  числом позиций, а не размером категории. Поэтому `tail_max_page: 600`;
- ссылка на карточку — `/product/<slug>-<sku>/?at=...`. SKU берётся из URL
  (`sampling.sku_from_url`), а не из вёрстки;
- slug в адресе категории роли не играет: Ozon определяет категорию по
  числовому id (`/category/kofemashiny-10680/` открывает «Утюги»). Адреса в
  `config.yaml` проверены через поиск Ozon.

### Выдача категории wildberries.ru

`python -m price_panel discover --marketplace wb`, категории — в
`marketplaces.wb.categories`, источник `wb_catalog`
(`marketplaces/wb/catalog.py`). Как и сбор цен WB, работает только при
`marketplaces.wb.enabled: true`.

Выдачу сайт получает запросом

```text
/__internal/u-search/exactmatch/ru/common/v18/search?query=menu_v3_<id меню> <название>&page=N
```

Что выяснено на живом сайте (11.10.2026):

- **по 100 товаров на страницу**, сортировка `popular`. У смартфонов сотая
  страница уже пуста — выдача кончается раньше (`tail_max_page: 99`, точная
  глубина приходит из пустых страниц, как у Ozon);
- **свои запросы выдачи WB терпит недолго**. С чужим `query` — сразу 498:
  со страницы музыкальных инструментов нельзя запросить выдачу кофемашин. С
  тем же запросом сайта, где менялся только `page`, — около шести за сессию,
  дальше 498 (18:39, пауза 5 с), и повторный показ страницы категории после
  каждых 4 запросов с паузой 8 с этого не изменил (19:25). Поэтому источник
  своих запросов выдачи не делает: он открывает страницу категории с
  `page=N` (`…?xsubject=631%3B1188&page=7`), как посетитель, и берёт ответ на
  запрос, который сделал для этой страницы сам сайт. Если сайт загрузил не ту
  страницу, она пропускается, а не выдаётся за нужную;
- меню WB крупнее, чем у Ozon: узкие категории — это **предметы**
  (`subject`), фильтр `xsubject`. Сайт берёт его из адреса страницы
  (`…/prigotovlenie-napitkov?xsubject=631;1188` → 2740 товаров, только
  кофеварки и кофемашины), поэтому фильтр пишется прямо в `url` категории;
- общей категории чехлов у WB нет — только по моделям телефонов. Для
  `phone_cases` взят поиск «чехол для телефона» с предметом 390 «Чехлы»
  (119 813 товаров); это выдача поиска, а не каталога;
- отказ WB (403 / 429 / 498) — остановка без повторов и ожиданий: капчу и
  проверки discovery не решает, найденное сохраняется, следующие категории не
  запускаются (`stopped`).

Соответствие категориям Ozon:

| Категория            | Страница WB                               | Предметы (`xsubject`) |
| -------------------- | ----------------------------------------- | --------------------- |
| `phone_cases`        | поиск «чехол для телефона»                | 390 Чехлы             |
| `smartphones`        | Электроника / Смартфоны и телефоны / Смартфоны | — (уже один предмет, 515) |
| `coffee_machines`    | Бытовая техника / Техника для кухни / Приготовление напитков | 631 Кофеварки, 1188 Кофемашины |
| `string_accessories` | Дом / Досуг и творчество / Профессиональные музыкальные инструменты | 3333 Струны, 6812 Аксессуары для музыкальных инструментов |

`string_accessories` у WB шире, чем у Ozon: в предмет 6812 входят и
аксессуары для духовых и ударных. У `coffee_machines` всего ~28 страниц,
поэтому `tail_items_per_page: 8`.

## Алгоритм для категории

```text
открыть страницу категории (в новой сессии браузера)
  -> top:  страницы 1, 2, ... подряд, пока не наберётся top_size новых SKU
  -> tail: случайные страницы из [после зоны top .. tail_max_page],
           с каждой не больше tail_items_per_page товаров
           (пустая страница = выдача кончилась, диапазон сужается)
  -> SKU из URL -> дедупликация (в том числе с другими категориями panel)
  -> запись в sku_panel: position, page, sampling_group
```

`position` — оценка места в выдаче: `(страница − 1) × 8 + место на странице`
(у WB — `× 100`).
Итог каждой категории (запросов, найдено, отобрано, seed) пишется в
`discovery_runs`. Пилотная panel из 80 SKU потребовала 29 запросов к листингу.

## Темп запросов и реакция на блокировки

Запрашиваются только нужные страницы, строго последовательно. Параметры темпа
в `config.yaml` подобраны по живому опыту:

- **Пауза.** `request_delay` = 5 с от конца предыдущего запроса, со случайным
  разбросом ±30 % (`request_jitter`). Между категориями — `category_pause`
  = 60 с.
- **Почему не быстрее.** Первая версия шла с паузой 2 с от начала запроса и
  при сборе полной panel в Docker (29.09.2026) после ~110 запросов получила
  **HTTP 403 на все запросы к выдаче**. Одна категория собралась, три — нет.
- **Отдельная сессия браузера на категорию.** Во втором прогоне в Docker
  (уже с паузой 5 с) картина повторилась: `smartphones` в свежем браузере
  собралась целиком (79 страниц без единого предупреждения), а
  `coffee_machines` в той же сессии получила 403 на первом же запросе и не
  получила ответа за 10 минут ожидания. Оба раза блок начинался на смене
  категории внутри одной сессии, а не после определённого числа запросов
  (110 и 81) или минут (4 и 8). Поэтому каждая категория обходится в новом
  контексте браузера (чистые cookies и состояние, cookies из `cookies.json`
  загружаются заново). **Это вывод из двух прогонов, а не документированное
  поведение Ozon.** С этим изменением оставшиеся две категории собрались
  подряд в одном запуске (30.09.2026, 79 и 76 страниц) без единого отказа.
- **Отказ Ozon** (403 / 429 / антибот-заглушка вместо JSON). Короткие повторы
  его только продлевают, поэтому discovery ждёт по списку `block_backoff`
  (10 с, 1, 3, 5 мин) и каждый раз повторяет в **новой** сессии браузера.
- **Если ограничение не снялось,** discovery сохраняет в panel всё, что уже
  нашёл, в том числе частично собранную категорию, и не трогает следующие
  категории (статус `stopped`). Повторный `discover` через 30–60 минут
  пропустит готовое и доберёт недостающее.
- **Обычные сбои** (обрыв, пустой ответ) — 2 коротких повтора (`MAX_RETRIES`),
  после чего страница пропускается.

## Sampling

**Почему несколько категорий.** Цены в разных нишах ведут себя по-разному:
дешёвые массовые товары с сотнями продавцов (чехлы), дорогая электроника с
частыми акциями (смартфоны), товары длительного пользования (кофемашины),
узкая ниша с малым спросом (аксессуары для струнных инструментов). Одна
категория показала бы динамику одного типа рынка.

**Почему top + tail, а не первые N.** Верх выдачи — самые популярные и
продвигаемые карточки, в том числе рекламные. Panel только из них показала
бы, как меняются цены лидеров, а не категории. Поэтому доля `top_ratio`
(по умолчанию 0.4) panel — первые позиции выдачи (`sampling_group = top`), а
остальное — случайные товары со случайных глубоких страниц
(`tail_random`). С одной страницы хвоста берётся не больше 3 товаров
(`tail_items_per_page`), чтобы выборка растянулась по глубине, а не собралась
с пары страниц. Категория `phone_cases` 29.09.2026 собрана ещё с 2 товарами
со страницы. Доли, глубина и зерно генератора задаются в `config.yaml`.

Генератор случайных чисел инициализируется парой `(discovery.seed, категория)`:
при той же выдаче Ozon случайная часть воспроизводится.

## Стабильность panel

Динамика цен имеет смысл только на одних и тех же товарах: если каждый день
брать новую случайную выборку, изменение «средней цены» будет отражать смену
состава, а не движение цен. Поэтому:

- повторный `discover` не трогает уже активные SKU: upsert обновляет только
  выключенные строки. Если категория набрана до `panel_size`, discover её
  пропускает без браузера и без запросов к Ozon;
- если `panel_size` увеличить, discover **доберёт** недостающие SKU в каждой
  группе, не меняя существующих;
- полная пересборка возможна только явно: `discover --rebuild`. Старые строки
  не удаляются, а выключаются (`is_active = false`), история по ним остаётся;
- SKU уникален во всей panel: товар, найденный в двух категориях, попадает
  только в первую.

## Dataset bias

Выборка формируется из ранжированной выдачи Ozon и поэтому не является
статистически случайной выборкой всех товаров площадки. Panel предназначена
для наблюдения динамики выбранного набора товаров во времени, а не для оценки
всей генеральной совокупности Ozon.

Конкретнее:

- кандидаты — только то, что Ozon показывает в выдаче категории при
  сортировке «Популярные». Товары без остатка, скрытые и не попавшие в выдачу
  в неё не входят;
- глубина ограничена самим Ozon (выдача обрывается на нескольких тысячах
  позиций) и настройкой `tail_max_page`. Длинный хвост категорий с сотнями
  тысяч товаров недоступен;
- «случайный хвост» случаен относительно ранжирования Ozon, а оно зависит от
  продаж, рекламы и персонализации (выдача немного меняется от запроса к
  запросу);
- категории выбраны вручную, их 4, и они не представляют Ozon в целом;
- со временем panel «стареет»: товары снимаются с продажи и становятся
  недоступными. Это видно по `is_available` и ошибкам `not_found`. Подмена
  выбывших SKU намеренно не автоматическая.
